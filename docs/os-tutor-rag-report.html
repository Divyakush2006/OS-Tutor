Abstract

This report describes OS Tutor, a tutor for Operating Systems built on Qwen3-4B-Instruct-2507 and fine-tuned with QLoRA on 11,760 curated training rows. The model is surrounded by three supporting components. Verified simulators compute the answer to every numerical problem, a retrieval (RAG) layer grounds concept explanations in course notes and cites them, and a fact checker corrects known misconceptions. On a 57-item hand-written problem suite the complete system scores 57/57, compared with 30/57 for the untuned model, and on a 600-item out-of-distribution holdout it scores 98.8%.

The RAG layer is built and connected to the tutor, and runs over a corpus of 105 documents: our professor's 42 course documents (lecture slides, assigned textbook chapters, handouts and lab material) plus openly licensed OS texts (Hailperin's Operating Systems and Middleware and 55 Wikipedia articles). On 124 labelled questions the correct passage is in the top five results 79.0% of the time, and retrieval takes 8.3 ms (95th percentile) on the CPU. Answers cite their sources and say so when the course materials do not cover a question. On a 200-question theory test, retrieval did not change accuracy (92.0% with it, 93.0% without).

The report follows the order of the work: the datasets, how they were preprocessed, the implementation with code screenshots, the measured results, the problems we ran into, and what we would do differently.

Note on the Results

Every number in this report was produced by a script in the project repository; Appendix B lists the file each one comes from. Three points need to be kept in mind when reading them.

  • Who wrote the evaluation sets. The 164 retrieval questions and the 130 new theory MCQ items were written by the project team and have not yet been reviewed by the course instructor. They are marked unreviewed in the data files.
  • The faithfulness judge. Whether a cited sentence is supported by its passage was judged by the untuned base model. We checked a sample of 40 of its verdicts by hand and found it lenient (Section 4.8). The required human check by the instructor is still open.
  • Targets. Section 4.10 lists the targets set before the measurement next to what was measured. A target that was missed is reported as missed.

Three statements in our earlier documents are corrected here and explained in Section 5. No training artifact contains a "final training loss of 0.2710". The gain on the adjacent computer-science subjects is not statistically significant (p = 0.20), so it cannot be called transfer. And once the grader was fixed, the adapter's gain on the problem suite without the solver is not significant either (p = 0.56).

2.2 Cleaning, deduplication and decontamination

  • Analyse before cleaning. A rule is adopted only if the data supports it, and every verdict is written to reports/analysis/. Two bugs found this way are described in Section 5: a tutoring threshold that silently dropped all 1,508 OS tutoring rows, and a decontamination key that removed 58% of the tutoring rows.
  • Boilerplate is not contamination. A naive "any shared 13-gram" rule removed 58% of the procedural rows. Training and evaluation problems share template text: a Banker's table header alone appears in 428 rows. An evaluation n-gram therefore counts as contamination only when it is rare in training, appearing in at most 5 rows. The 93 boilerplate n-grams are ignored.
  • Generated rows are checked by their parameters, not their words. A leaked problem is the same problem however it is worded, so simulator rows are matched on an exact parameter fingerprint. That caught 15 reworded leaks that n-grams missed.

2.3 Selection, rendering, ordering and release gates

  • Ratios are proportions, not ceilings. In v1, the categories that came up short let the others' shares balloon: replay reached 31% against a 12% design. The build now scales the total to the scarcest category, which is tutoring. Measured mixture drift is ≤ 0.02 percentage points.
  • Rectifier ordering. No more than 4 consecutive rows come from one category, and no more than 3 from one source across 81 sources (measured: 1). Replay is spaced every 4 rows early in training and every 14 late (FOREVER, arXiv 2601.03938). The order matters, so training uses a sequential sampler.
  • Surprise-ranked replay. Replay rows are chosen by their per-token NLL under the base model (SuRe, arXiv 2511.22367), not by a hand-written quality heuristic.
  • Release gates (19/19 pass). The gates cover: no secrets, no <think> blocks, no non-commercial rows, schema validity, token p99 ≤ 16,384 (measured 2,753; longest row 11,648, so nothing is truncated), rectifier invariants, mixture drift, distinct-answer ratio, template share, diversity, OOD holdout present, procedural inputs complete, and OS tutoring present.

3.4 Verified solver

The model never carries out a procedure. It reads the question into typed JSON. This step runs on the untuned base at LoRA scale 0, which reads more reliably: 84% extraction accuracy against 79% for the adapter. Every extracted number must then appear in the question. Grounded parameters go to a simulator, which computes the answer; anything ungrounded falls back to the model.

3.5 RAG pipeline

The pipeline has four files. extract.py turns PDF, PPTX, DOCX, Markdown and text into Markdown whose headings are the citation anchors. corpus.py validates the manifest and cuts the documents into citable chunks. retrieve.py ranks the chunks, decides whether any of them are relevant, and builds the prompt. ingest.py is the command the course staff use to add material (add) and rebuild the index.

The abstain gate. A passage that is only the least-bad match is worse than no passage, because the model would cite it as support. The gate keeps the passages if either signal is strong: the best dense similarity, or the best BM25 score. BM25 scores grow with the size of the corpus, so the two thresholds are fitted for each corpus. For the course corpus they are cosine ≥ 0.59 or BM25 ≥ 18.5, fitted on the dev half of the questions only (Figure 14).

3.6 Gateway integration

Retrieval is layer 2 of the gateway. It runs after the simulator layer, so a solvable problem is still computed and retrieval is not even consulted for it (a gateway test checks this). It runs before the fact checker, which checks the grounded draft. Only explain and analyze retrieve. Tutor mode never does, because a passage could state the answer the student is working towards. Retrieval is switched on by OSTUTOR_RAG=data/rag/corpus; a gateway started without it behaves exactly as before. Answers end with a "Sources from your course notes" list. When the gate abstains, they end instead with "Not found in the course materials", so general knowledge is never passed off as course content.

3.7 Evaluation and tests

Every comparison in the project is paired: the same items are scored under two configurations. The right test for a paired yes/no outcome is McNemar's, and with 5–30 discordant items the exact binomial form is needed.

Four test suites need no GPU: tools/test_pipeline.py (data pipeline), tools/test_router.py (28 labelled routing cases, 0 misroutes allowed on shown attempts), tools/test_g0.py (55 checks on statistics, extraction scoring, grader regressions and the one-adapter guard), and tools/test_rag.py (46 checks). The gateway suite grew from 28 to 37 checks.

Ten probes were run, one per correction rule, and every v3 answer was read by hand. Reading the results.

  • The MCQ target was not met, and retrieval made no measurable difference. The target was "v3 with retrieval ≥ base"; it scored 184 against 185, and the difference is one question (p = 1.0). All four configurations are within two questions of each other. The base model already answers 92.5% of these questions correctly without notes, so there is little left for notes to fix. On this larger set the fine-tuned model is also no worse than the base, unlike the 70-item log-likelihood result.
  • Citations are honest but sparse. No answer cited a note that does not exist, and 50 of 59 answers cited at least once. But only 132 of the 446 answer sentences carry a citation. The rest are the model's own explanation, which the student cannot check against the notes.
  • About 60% of cited sentences are fully supported on our strict reading: everything the sentence says must be in the cited passage. The usual failure is a correct quotation followed by the model's own elaboration in the same sentence, or an example the passage does not contain. One answer quoted a passage accurately and then added a worked address example with wrong arithmetic. The base-model judge is too lenient: where we disagreed with it, it had said "supported" 8 times and we had said so 3 times. So its 81.8% overstates faithfulness.
  • Speed is unaffected. A median prompt of 816 tokens, most of it retrieved notes, did not slow decoding (42.9 tok/s against the 20 tok/s floor). These are server-reported decode rates and exclude prompt processing, which is why they differ from the 26.9 tok/s wall-clock figure measured earlier through the full stack.

4.9 Discussion

  • Each layer guards a different failure. The simulator guards procedures: a 4B model cannot execute a long schedule reliably, but it can read one. Retrieval ties declarative claims to passages the student can check. The fact checker guards a known list of misconceptions. Tutor mode is shielded from all three, because its job is to withhold the answer.
  • Fine-tuning's measured value is narrower than first claimed. With the solver, the adapter adds 8 significant items. Without it, there is no significant gain over the untuned base on the problem suite, and none on the 200-item theory set. Its other contributions are the trained output formats, the Socratic behaviour and the shell mode, and none of these is yet measured by a number (G3).
  • Retrieval's value is traceability, not accuracy, so far. It did not raise MCQ accuracy, which was already near its ceiling. What it adds is an answer tied to the course's own slides and readings, with the source named, and an explicit warning when the course does not cover the question. Whether that helps students learn is not measured yet.
  • Measurement found more errors than the model did. Two grader blind spots, a non-deterministic cache, a void benchmark, two unsupported claims and a lenient faithfulness judge all biased the numbers in the project's favour. Each was found by auditing the evaluation rather than the model (Section 5).

5.4 Errors in engineering process

  • A benchmark chain waited an hour polling itself. busy("benchmark.py") matched run_full_benchmark.py. Polling for a free GPU between jobs also raced and crashed the next job. Fixed: match the full path, and require several consecutive clear polls.
  • Git normalised 57 CRLF files to LF. The repository was staged before line-ending conversion was disabled, which would have silently changed bytes the dataset manifest hashes. Fixed and verified file by file (D-001).
  • The evaluation questions are ours. The retrieval questions and the new MCQ items were written by the team, not by the instructor, and were written while looking at the passages. We tried to phrase them as students would, but they are likely easier than real student questions.
  • Wikipedia article identifiers lost characters. "Bélády's anomaly" became wiki-b-l-dy-s-anomaly and "Producer–consumer" lost its dash, which broke two question labels. Titles are now transliterated before the identifier is made.

6.  Alternative Flow (Improvements)

For each stage: what we would do differently with hindsight, or next, and the evidence that motivates it.

6.1 Evaluate before training, not after

The biggest lesson is ordering. The project trained three adapters before it measured the untuned base on the same suite with the same grader. Done the other way round, the ablation would have shown on day one that the solver, not more fine-tuning, was the lever. A better flow:

  1. Build the evaluation sets and the grader, then audit the grader on the base model's outputs.
  2. Measure the base model, deterministically, with a significance test for every comparison.
  3. Add tools (solver, retrieval) and measure again.
  4. Fine-tune only for the gaps tools cannot close, and state the expected effect size first.

6.2 Data

  • Targeted declarative replay for the OS-theory topics that regressed, or a LoRA-scale sweep, so theory accuracy can recover to ≥ base without retraining everything.
  • Grow tutoring supply with genuine material. Tutoring is the scarcest category and bounds the whole dataset. Rewordings would add memorisation pressure, not supply.
  • Harder theory questions. The 200-item set now exists, but every configuration scores 92–93% on it, so it can no longer separate them. Questions that need reasoning across concepts, written or reviewed by the instructor, would show differences that this set cannot.

6.3 Model

  • Zero-shot probe newer bases (Qwen3.5-4B, Gemma 4 12B, non-thinking) on the theory MCQ before any retraining, with Qwen3-4B-2507 as control.
  • Merge the LoRA before quantising. Runtime LoRA is the likely reason decode speed is below the card's bandwidth bound. Speculative decoding with a 0.6B draft model is a second option.

6.4 Retrieval

  • Make the model cite every sentence it takes from the notes. The prompt currently asks for citations "where the answer relies on the notes"; a stricter instruction, or a short worked example of a fully cited answer, should raise the 132-of-446 coverage. The change should be compared on the dev questions before being reported on the test half.
  • Check answers against their sources before showing them. Split the answer into sentences and drop or flag any cited sentence its passage does not support. A stronger judge than the 4B base model is needed for that: our check found the current one too lenient.
  • Questions from the instructor and from students. Real questions, labelled by the instructor with every passage that answers them (not just one), would give a fairer recall figure than our single-passage labels.
  • A re-ranker rather than a bigger embedder. A larger embedder bought 2.5 points of recall that were not significant. A small cross-encoder that re-scores the top 20 attacks the actual weakness, which is ranking the right passage first (recall@1 is 46%).
  • Learned or calibrated abstention. Use a logistic model over (max cosine, max BM25, margin between the top two) instead of hand-set thresholds, with precision and recall reported on held-out data.
  • Grounding checks on the answer, not just the prompt. Verify that each cited sentence is supported by the cited passage (entailment, or overlap as a first step). The fact checker becomes a check against the notes instead of a fixed rule list.
  • Retrieval for tutor hints, but behind a leak filter. Passages could make Socratic hints more accurate, but only if a filter guarantees no passage states the final answer. That needs its own answer-leak measurement first (G3).

6.5 Verification and serving

  • Fix the disk off-by-one and add a range-semantics check to grounding, not just a presence check.
  • Negation-aware fact checking, with every rule exercised by a probe in the test suite.
  • Run the fact checker on streamed answers: buffer prose answers, or check and append a correction after the stream ends.
  • Extend delegation to the 11 formula kinds, which are still answered by the model unaided.

6.6 Process

  • Every reported number names its file, and documents are generated from those files rather than typed by hand. The two incorrect PDF claims would not have been possible.
  • Version control from the first day, with byte-exact storage and a commit hash in every report.
  • Every evaluation run records its provenance (commit, model hashes, server arguments, decoding settings, cache setting), as the G0 harness now does.
