Abstract

This report describes OS Tutor, a tutor for Operating Systems built on Qwen3-4B-Instruct-2507 and fine-tuned with QLoRA on 11,760 curated training rows. The model is surrounded by three supporting components. Verified simulators compute the answer to every numerical problem, a retrieval (RAG) layer grounds concept explanations in course notes and cites them, and a fact checker corrects known misconceptions. On a 57-item hand-written problem suite the complete system scores 57/57, compared with 30/57 for the untuned model, and on a 600-item out-of-distribution holdout it scores 98.8%.

The RAG layer has been implemented, tested and connected to the tutor. Retrieval runs on the CPU in under 7 ms per query. The course notes from the institution have not yet been supplied, so all retrieval results in this report were measured on a small set of test notes written by us. These results are therefore an upper bound, and the figures we expect on the real notes are given separately as targets.

The report follows the order of the work: the datasets, how they were preprocessed, the implementation with code screenshots, the measured results, the problems we ran into, and what we would do differently.

Note on the Results

Every number in this report was produced by a script in the project repository; Appendix B lists the file each one comes from. Two kinds of number need to be read with care.

  • Results on the test notes. Until the course notes are supplied, retrieval runs over 12 short OS notes that we wrote ourselves for testing, with 55 labelled questions. Because the same people wrote the notes and the questions, these numbers are an upper bound for what the real notes will give.
  • Targets. What we expect, or require, once the course notes are available (Section 4.10). These have not been measured and are not presented as results.

Three statements in our earlier documents are corrected here and explained in Section 5. No training artifact contains a "final training loss of 0.2710". The gain on the adjacent computer-science subjects is not statistically significant (p = 0.20), so it cannot be called transfer. And once the grader was fixed, the adapter's gain on the problem suite without the solver is not significant either (p = 0.56).

2.2 Cleaning, deduplication and decontamination

  • Analyse before cleaning. A rule is adopted only if the data supports it, and every verdict is written to reports/analysis/. Two bugs found this way are described in Section 5: a tutoring threshold that silently dropped all 1,508 OS tutoring rows, and a decontamination key that removed 58% of the tutoring rows.
  • Boilerplate is not contamination. A naive "any shared 13-gram" rule removed 58% of the procedural rows. Training and evaluation problems share template text: a Banker's table header alone appears in 428 rows. An evaluation n-gram therefore counts as contamination only when it is rare in training, appearing in at most 5 rows. The 93 boilerplate n-grams are ignored.
  • Generated rows are checked by their parameters, not their words. A leaked problem is the same problem however it is worded, so simulator rows are matched on an exact parameter fingerprint. That caught 15 reworded leaks that n-grams missed.

2.3 Selection, rendering, ordering and release gates

  • Ratios are proportions, not ceilings. In v1, the categories that came up short let the others' shares balloon: replay reached 31% against a 12% design. The build now scales the total to the scarcest category, which is tutoring. Measured mixture drift is ≤ 0.02 percentage points.
  • Rectifier ordering. No more than 4 consecutive rows come from one category, and no more than 3 from one source across 81 sources (measured: 1). Replay is spaced every 4 rows early in training and every 14 late (FOREVER, arXiv 2601.03938). The order matters, so training uses a sequential sampler.
  • Surprise-ranked replay. Replay rows are chosen by their per-token NLL under the base model (SuRe, arXiv 2511.22367), not by a hand-written quality heuristic.
  • Release gates (19/19 pass). The gates cover: no secrets, no <think> blocks, no non-commercial rows, schema validity, token p99 ≤ 16,384 (measured 2,753; longest row 11,648, so nothing is truncated), rectifier invariants, mixture drift, distinct-answer ratio, template share, diversity, OOD holdout present, procedural inputs complete, and OS tutoring present.

3.4 Verified solver

The model never carries out a procedure. It reads the question into typed JSON. This step runs on the untuned base at LoRA scale 0, which reads more reliably: 84% extraction accuracy against 79% for the adapter. Every extracted number must then appear in the question. Grounded parameters go to a simulator, which computes the answer; anything ungrounded falls back to the model.

3.5 RAG pipeline

The pipeline has three files. corpus.py validates the manifest and cuts the notes into citable chunks. retrieve.py ranks the chunks, decides whether any of them are relevant, and builds the prompt. __init__.py documents the design.

The abstain gate. A passage that is only the least-bad match is worse than no passage, because the model would cite it as support. When the gate decides the notes do not cover the question, retrieval returns nothing, and the answer is generated exactly as without RAG. The first gate (v1) used only the dense similarity, and it failed on the fixture (Section 4.7). The served gate (v2) keeps the passages if either signal is strong: cosine ≥ 0.45 or BM25 ≥ 6.0.

3.6 Gateway integration

Retrieval is layer 2 of the gateway. It runs after the simulator layer, so a solvable problem is still computed, and before the fact checker, which checks the grounded draft. Only explain and analyze retrieve. Tutor mode never does, because a passage could state the answer the student is working towards. Retrieval is switched on by OSTUTOR_RAG=<corpus dir>; a gateway started without it behaves exactly as before. Answers end with a "Sources from your course notes" list, in both the streamed and the non-streamed path.

3.7 Evaluation and tests

Every comparison in the project is paired: the same items are scored under two configurations. The right test for a paired yes/no outcome is McNemar's, and with 5–30 discordant items the exact binomial form is needed.

Four test suites need no GPU: tools/test_pipeline.py (data pipeline), tools/test_router.py (28 labelled routing cases, 0 misroutes allowed on shown attempts), tools/test_g0.py (55 checks on statistics, extraction scoring, grader regressions and the one-adapter guard), and the new tools/test_rag.py (29 checks). The gateway suite grew from 28 to 34 checks.

4.6 Fact checker

Ten probes were run, one per correction rule, and every v3 answer was read by hand. The checker produced 1 true positive, 2 false positives, 1 false negative and 6 true negatives, so precision is 1/3 and recall is 1/2. Both false alarms were correct negated sentences: the rules match "suffers from Belady's anomaly" without seeing the "does not" before it. The miss was seg_internal_frag. On a broader set of 70 theory answers it flagged 0. Source: reports/g0/20261012-1429/factcheck_v3.json.

  • Latency is not a concern. p95 is 5.7 ms against the brief's 500 ms.
  • The v1 gate failed. It was chosen before any measurement, and it let 4 of the 10 off-topic questions retrieve OS passages. Dense similarity alone cannot separate the two classes: in-scope questions go as low as 0.34 and out-of-scope ones as high as 0.40.
  • The v2 gate is optimistic. It was fitted on these same 55 questions, so its 10/10 is not an independent result. It must be refitted on held-out questions over the real notes.
  • BM25 beat the hybrid on the fixture. The likely reason: the same person wrote the notes and the questions, so they share vocabulary. Real student questions will paraphrase more, which is the case the dense half exists for. The decision stays open until real-notes data exists.
  • Both remaining misses are false abstentions on terse questions: "Is SRTF preemptive?" and "When is busy waiting acceptable?". The answer is then generated without notes, which is the safe failure.

4.8 RAG: end to end on the served model

@@E2E@@

Reading the results.

  • Citations behave as designed. 41 of 43 answers that were given notes cited them, and no answer cited a note that does not exist. The two that did not cite (SSTF starvation, invoking a system call) still restated the note's content. All 10 off-topic questions received no notes, so their answers were generated exactly as without RAG.
  • RAG fixed a misconception the fine-tuned model holds. Asked "Can LRU suffer from Belady's anomaly?", the model without notes answered "Yes, LRU (Least Recently Used) can suffer from Belady's anomaly", which is wrong and was flagged by the fact checker. With notes it answered "No, LRU … does not suffer from Belady's anomaly [S1]" and gave the stack-algorithm reason from the note. That was the only fact-checker flag in either arm (1 off, 0 on, of 55).
  • No measurable effect on the theory MCQ. Both arms scored 65/70, with one flip each way (p = 1.0), including on the 53 items where notes were retrieved. At 93% the model is near the ceiling of this set in this protocol, so the MCQ cannot show a gain. A harder 200-item set is needed (G3).
  • Speed is unaffected. Decoding stayed at ~43 tok/s with about 380 extra prompt tokens; the slowest answer with RAG was 41.7 tok/s, against a 20 tok/s floor. These are server-reported decode rates and exclude prompt processing, which is why they differ from the 26.9 tok/s wall-clock figure measured earlier through the full stack.
  • Truncation affects the length and time figures. The run capped answers at 700 tokens. 28 of 55 answers without notes hit the cap, against 7 of 55 with notes. So the shorter, faster answers with RAG (median 225 tokens, 5.5 s, against 700 tokens and 16.2 s) are partly an artefact of truncation. They show that grounded answers are more focused; they do not give a clean measure of speed-up.

4.9 Discussion

  • Each layer guards a different failure. The simulator guards procedures: a 4B model cannot execute a long schedule reliably, but it can read one. Retrieval guards declarative claims by tying each one to a passage the student can check. The fact checker guards a known list of misconceptions. Tutor mode is shielded from all three, because its job is to withhold the answer.
  • Fine-tuning's measured value is narrower than first claimed. With the solver, the adapter adds 8 significant items. Without it, there is no significant gain over the untuned base. Its other contributions are the trained output formats, the Socratic behaviour and the shell mode, and none of these is yet measured by a number (G3).
  • RAG addresses the one measured weakness. Declarative OS knowledge is the area where fine-tuning did not help and may have slightly hurt (85.71% vs 90.00%, not significant). Retrieval is the brief's recommended remedy for exactly this, and Section 4.8 tests it.
  • Measurement found more errors than the model did. Two grader blind spots, a non-deterministic cache, a void benchmark and two unsupported claims all biased the numbers in the project's favour. Each was found by auditing the evaluation rather than the model (Section 5).

5.4 Errors in engineering process

  • A benchmark chain waited an hour polling itself. busy("benchmark.py") matched run_full_benchmark.py. Polling for a free GPU between jobs also raced and crashed the next job. Fixed: match the full path, and require several consecutive clear polls.
  • Git normalised 57 CRLF files to LF. The repository was staged before line-ending conversion was disabled, which would have silently changed bytes the dataset manifest hashes. Fixed and verified file by file (D-001).
  • RAG fixture is not independent. The notes and questions share an author, and the v2 gate was fitted on them. This is acknowledged in every RAG number, but it is a real limitation.

6.  Alternative Flow (Improvements)

For each stage: what we would do differently with hindsight, or next, and the evidence that motivates it.

6.1 Evaluate before training, not after

The biggest lesson is ordering. The project trained three adapters before it measured the untuned base on the same suite with the same grader. Done the other way round, the ablation would have shown on day one that the solver, not more fine-tuning, was the lever. A better flow:

  1. Build the evaluation sets and the grader, then audit the grader on the base model's outputs.
  2. Measure the base model, deterministically, with a significance test for every comparison.
  3. Add tools (solver, retrieval) and measure again.
  4. Fine-tune only for the gaps tools cannot close, and state the expected effect size first.

6.2 Data

  • Targeted declarative replay for the OS-theory topics that regressed, or a LoRA-scale sweep, so theory accuracy can recover to ≥ base without retraining everything.
  • Grow tutoring supply with genuine material. Tutoring is the scarcest category and bounds the whole dataset. Rewordings would add memorisation pressure, not supply.
  • A 200-item theory MCQ, so a 4-point change no longer hinges on 5 questions.

6.3 Model

  • Zero-shot probe newer bases (Qwen3.5-4B, Gemma 4 12B, non-thinking) on the theory MCQ before any retraining, with Qwen3-4B-2507 as control.
  • Merge the LoRA before quantising. Runtime LoRA is the likely reason decode speed is below the card's bandwidth bound. Speculative decoding with a 0.6B draft model is a second option.

6.4 Retrieval

  • Collect held-out real questions first. At least 100 owner-written questions over the course notes, labelled with note and section, half for fitting the gate and half for reporting.
  • Try a stronger embedder if recall is low. bge-code-v1, multilingual-e5-base and Qwen3-Embedding-0.6B are already in the local cache. Add a small cross-encoder re-ranker over the top 10 if section recall@1 is the bottleneck.
  • Learned or calibrated abstention. Use a logistic model over (max cosine, max BM25, margin between the top two) instead of hand-set thresholds, with precision and recall reported on held-out data.
  • Grounding checks on the answer, not just the prompt. Verify that each cited sentence is supported by the cited passage (entailment, or overlap as a first step). The fact checker becomes a check against the notes instead of a fixed rule list.
  • Retrieval for tutor hints, but behind a leak filter. Passages could make Socratic hints more accurate, but only if a filter guarantees no passage states the final answer. That needs its own answer-leak measurement first (G3).

6.5 Verification and serving

  • Fix the disk off-by-one and add a range-semantics check to grounding, not just a presence check.
  • Negation-aware fact checking, with every rule exercised by a probe in the test suite.
  • Run the fact checker on streamed answers: buffer prose answers, or check and append a correction after the stream ends.
  • Extend delegation to the 11 formula kinds, which are still answered by the model unaided.

6.6 Process

  • Every reported number names its file, and documents are generated from those files rather than typed by hand. The two incorrect PDF claims would not have been possible.
  • Version control from the first day, with byte-exact storage and a commit hash in every report.
  • Every evaluation run records its provenance (commit, model hashes, server arguments, decoding settings, cache setting), as the G0 harness now does.
